## Doctor, backup, and restore

- Doctor: Doctor imports the canonical registry directly, uses the no-source-write preflight, and emits separate bounded evidence for invalid user_version, missing history, gap or duplicate, unknown name, checksum mismatch, noncanonical known history, conversion DDL/index/trigger or row/digest mismatch, unauthorized provenance shape, partial conversion, invalid reindex control DDL, invalid lease/progress/counter/replacement overlay, and newer schema. It never accepts caller-supplied migration definitions, touches source sidecars, or erases one finding behind another.

- Backup: The production backup service pauses all database writers, verifies exact canonical version 27, history, byte-exact conversion infrastructure and rows, and reindex overlay before serialization, then reopens the serialized snapshot and verifies the same bytes/digests. A valid active reindex overlay is resumable and may be backed up; a legacy, partial, corrupt, unknown, provenance-invalid, or newer database is not published as a new backup.

- Empty-root restore: Restore verifies manifest, artifact hashes, SQLite integrity, foreign keys, exact canonical version 27, exact canonical history, byte-exact conversion table/index/triggers and every row re-encoding/digest, and any active reindex overlay before the final rename. It never migrates or repairs a backup during restore.

- Full restore: Offline root replacement invokes the same registry verifier on the staged root before swap and again through repository verification after swap. Registry failure preserves the live root or rolls it back, with target, stage, and rollback disposition reported.

- Historical backup rule: A historical backup must first be upgraded by the matching application version into a newly verified canonical backup. Restore does not infer or convert history.
