## Doctor, backup, and restore

- Doctor: Doctor imports the canonical registry directly, uses the no-source-write preflight, and emits separate bounded evidence for the live full-registry version/digest, explicit historical target-27 version/digest, invalid user_version, missing history, gap or duplicate, unknown name, checksum mismatch, noncanonical known history, conversion DDL/index/trigger or row/digest mismatch, unknown target, full-digest-substituted target, unauthorized provenance shape, partial conversion, invalid reindex control DDL, invalid lease/progress/counter/replacement overlay, and newer schema. It never accepts caller-supplied migration definitions, touches source sidecars, or erases one finding behind another.

- Backup: The production backup service pauses all database writers, verifies the exact current canonical version and history, byte-exact conversion infrastructure and rows including explicit append-stable target 27, and reindex overlay before serialization, then reopens the serialized snapshot and verifies the same bytes/digests. A valid active reindex overlay and valid target-27 row are resumable and may be backed up after suffix append; a legacy, partial, corrupt, unknown-target, full-digest-substituted, provenance-invalid, or newer database is not published as a new backup.

- Empty-root restore: Restore verifies manifest, artifact hashes, SQLite integrity, foreign keys, exact current canonical version/history, byte-exact conversion table/index/triggers and every row re-encoding/digest including explicit append-stable target 27, and any active reindex overlay before the final rename. An unknown or full-digest-substituted target rejects. Restore never migrates or repairs a backup.

- Full restore: Offline root replacement invokes the same explicit accepted-target verifier on the staged root before swap and again through repository verification after swap. An unknown or full-digest-substituted target preserves the live root or rolls it back, with target, stage, and rollback disposition reported.

- Historical backup rule: A historical backup must first be upgraded by the matching application version into a newly verified canonical backup. Restore does not infer or convert history.
