# iCloud credential authority V1 decisions

> Generated by `icloud-credential-authority-check.v1.mjs --write-views`. Do not edit by hand.
> Normative source: [icloud-credential-authority-oracle.v1.json](./icloud-credential-authority-oracle.v1.json)
> Oracle SHA-256: `9b685e1293570d8f55f9a11c02b108e0ac5585a3cffdc367762db09f3e687c3c`

## Accepted decisions

- **D01** Use one dedicated Apple app-specific password for V1 and never the primary Apple Account password.

  Reason: Apple documents the path for manual iCloud IMAP clients and provides individual revocation.

- **D02** Infer one fixed TLS IMAP provider definition and a two-candidate username rule.

  Reason: Apple publishes the endpoint and fallback username form; setup need not ask protocol questions.

- **D03** Ship an intact notarized Homebrew Cask whose separately signed nested CLI, broker, and daemon precede manifest generation and whose outer bundle is signed last.

  Reason: The inside-out graph makes every manifest cdhash available before the outer seal and removes any self-reference while preserving profile-authorized app-like principals.

- **D04** Use the data-protection Keychain, AfterFirstUnlockThisDeviceOnly, non-synchronizing, in the logged-in user context.

  Reason: It permits unattended background reconnect after first unlock, denies pre-unlock access, and prevents cross-device migration.

- **D05** Give only broker and daemon the exact Keychain access group; CLI invokes the broker and stores only nonsecret authority.

  Reason: The native broker captures/administers while the daemon must resolve for unattended authentication; ordinary CLI and HTTP do not need direct Keychain access.

- **D06** Use challenge-first C XPC with symmetric per-message SecCode, exact requirement/cdhash, UID, audit-session, nonce-binding, expiry, and replay checks; require macOS 12+.

  Reason: A wrong peer learns only a random non-authority challenge and cannot cause operation decoding or UI, while both initiator and acceptor authenticate the actual received message.

- **D07** Generate an opaque random reference and bind it to installation, provider, revision, transaction, and metadata.

  Reason: Configuration can explain and recover exact authority without storing or discovering a secret.

- **D08** Make create/replace add-only and promote a new ref before exact-deleting the old ref.

  Reason: In-place update would collapse generation, rollback, and crash authority.

- **D09** Persist one nonsecret transaction before Keychain add and recover every boundary through one LocalAccountAuthorityActor.

  Reason: A durable exact ref prevents silent orphan/adoption and keeps cancellation/cleanup owned.

- **D10** Use the signed daemon binary in one-shot mode for production validation before registering the long-running LaunchAgent.

  Reason: The same Keychain resolver and ImapFlow factory are exercised without starting an unvalidated service or adding another credential principal.

- **D11** Pin ImapFlow 1.7.1 declarations and runtime; route discovery through the owned no-cast listIcloudMailboxesReadOnly adapter, which constructs ListOptions & { readonly listOnly: true }, behind a pre-dispatch command guard and capability-branch probes.

  Reason: The installed declarations omit listOnly, so the constructive intersection adapter makes literal true type-check without an excess-property call or escape hatch; the pinned runtime then returns before LSUB and STATUS while preserving one bounded LIST-or-XLIST result.

- **D12** Treat final full-address authentication rejection, local-part candidate rejection, missing item, first unlock, network, TLS, malformed provider, and internal failure as distinct safe categories.

  Reason: Only a final full-address rejection should enter the stable generation-gated blocked state.

- **D13** Only a strictly newer accepted revision can release authentication-blocked; no retry timer exists there.

  Reason: The current sync statechart already models this invariant and it prevents provider retry storms.

- **D14** Keep account operations in a strict local registry absent from HTTP, bearer, OpenAPI, and demo surfaces.

  Reason: Credential administration is machine-local user authority, not remote API authority.

- **D15** Use one typed local operation/outcome model for guided and structured paths; setup only orchestrates it.

  Reason: Agents receive stable semantics without a second credential implementation or plaintext unattended shortcut.

- **D16** Back up only nonsecret explanatory metadata and require reprovisioning after empty/different-device restore.

  Reason: ThisDeviceOnly credentials do not migrate and secret export would defeat the Keychain boundary.

- **D17** Journal complete removal targets before the first effect, confirm each exact item absent before removing its binding, and separate uninstall, archive deletion, and manual Apple revocation.

  Reason: Every crash can resume from finite authority and absent cannot hide a failed Keychain cleanup or imply server revocation.

- **D18** Make demo isolation structural and retain eight separate evidence tiers.

  Reason: Credential-free evaluation and honest release claims both require absence proofs, not mode flags or broad green suites.

- **D19** Share three total provider sessions and two delays across both username candidates for one credential generation.

  Reason: A candidate fallback must not reset the retry budget or turn a transient outage into an unbounded setup loop.

- **D20** Retain at most 256 unexpired mutation receipts for 24 hours, compact before admission, and reject unique request 257 before UI/effect.

  Reason: The cap is predictable under load while identical retries remain idempotent even at capacity.

- **D21** Freeze five nonoverlapping implementation modules with one sole actor/journal writer and a read-only qualification owner.

  Reason: Ownership prevents native, ImapFlow, presentation, and qualification work from silently creating parallel state or repair authority.

- **D22** Generate all three human-readable views from the oracle and byte-compare them in the checker.

  Reason: Token presence alone cannot prove that Markdown presents the exact machine-readable contract.

## Rejected alternatives

- **R01** primary Apple Account password

  Rejected because: forbidden by the accepted product boundary and unnecessary for documented IMAP access.

- **R02** environment, stdin, argv, shell, file, config, or generic secret-file injection

  Rejected because: creates plaintext transport/storage and qualification-only bypasses.

- **R03** system LaunchDaemon and file-based Keychain

  Rejected because: data-protection Keychain is user-context only and the accepted service is a user LaunchAgent.

- **R04** CLI Keychain entitlement

  Rejected because: widens direct secret access beyond the processes that capture or authenticate.

- **R05** HTTP/bearer credential administration

  Rejected because: would turn remote bearer authority into local credential authority.

- **R06** PID-only or UID-only broker authentication

  Rejected because: PID reuse and same-user processes do not prove accepted code identity.

- **R07** in-place Keychain update

  Rejected because: destroys rollback and credential-generation boundaries.

- **R08** automatic item enumeration/adoption

  Rejected because: could bind or delete unrelated/stale credentials without durable authority.

- **R09** automatic Apple revocation

  Rejected because: requires a separate Apple session/remote mutation not authorized for V1.

- **R10** Apple direct third-party authorization now

  Rejected because: support documentation describes supported apps but no current public developer enrollment/protocol authority was found.

- **R11** mock-only or broad-suite qualification

  Rejected because: cannot prove code signing, Keychain access, launchd, Apple, restore, or revocation.

- **R12** demo/live runtime fallback

  Rejected because: could inspect live authority or turn synthetic failure into production access.

- **R13** outer executable cdhash embedded in its own sealed manifest

  Rejected because: the final outer signature changes the CodeDirectory and makes construction self-referential.

- **R14** send operation metadata before a bidirectionally authenticated hello

  Rejected because: a wrong peer could learn intent or trigger UI before message-derived code identity is established.

- **R15** ImapFlow verifyOnly/includeMailboxes discovery, a direct excess-property object literal, or a cast/module augmentation that pretends listOnly is declared

  Rejected because: the installed 1.7.1 connect path calls list without listOnly and may expand subscription/status behavior, while the installed ListOptions declaration omits listOnly and must be extended constructively at the owned adapter boundary.

- **R16** remove binding before every exact Keychain item absence is confirmed

  Rejected because: a cleanup failure would discard the reference needed for bounded recovery.

- **R17** pseudo recorded-resume-state target

  Rejected because: it is not an implementable state or finite recovery dispatch.

- **R18** unbounded receipt growth or eviction of unexpired idempotency records

  Rejected because: either exhausts storage or permits a retry to repeat an accepted effect.

- **R19** three retries per username candidate

  Rejected because: candidate fallback would silently double the promised attempt budget.

- **R20** defer file and module ownership until implementation

  Rejected because: parallel work could create multiple journal writers or overlap security and qualification authority.
